# User deletion

This file is a flow of `ARCHITECTURE.md`, section 6. It says what happens, step by step. The rules it cites by id are in `ARCHITECTURE.md` and `api-catalog.md`.

A system admin deletes a user (A8), or the user deletes their own account (section 2). A user's memberships are under row level security, and a transaction declares one tenant (R4), so no transaction can check every tenant and change them together. The deletion runs in steps, each in a transaction of its own; the endpoint sends steps 1 to 3 one after the other. This is not a saga: the request waits for each of them and answers with the result (S1). Steps 4 and 5 follow the commit of step 3 as its messages, and the request does not wait for them.

## 1. A system admin's deletion

| Message | Sent by | Handled by | Handler has a transaction |
| --- | --- | --- | --- |
| `ListUserMembershipsQuery` | `DELETE /v1/platform/users/{userId}` | ControlPlane, `ListUserMembershipsHandler` | Yes; it declares the user (R11) |
| `GetLastOwnershipQuery` | the same endpoint, once for each tenant the user owns that is active, suspended, closed or purging | ControlPlane, `GetLastOwnershipHandler` | Yes, the tenant's |
| `RemoveUserMembershipCommand` | the same endpoint, once for each tenant the user is a member of | ControlPlane, `RemoveUserMembershipHandler` | Yes, the tenant's |
| `UserMembershipRemovedEvent` | `RemoveUserMembershipHandler` | Audit, `RecordUserMembershipRemovedHandler` (`member.removed`, tenant log, by the platform) | Yes |
| `WithdrawSignUpCommand` | `RemoveUserMembershipHandler` and `EraseFormerMemberHandler`, for each pending invitation they cancelled that has an identity provider invitation | ControlPlane, `WithdrawSignUpHandler` (calls the identity provider) | No |
| `DeleteUserCommand` | the same endpoint, last | ControlPlane, `DeleteUserHandler` | Yes; it declares the user (R11) |
| `UserDeletedEvent` | `DeleteUserHandler`, only for the first deletion | Audit, `RecordUserDeletedHandler` (`user.deleted`, platform log); Notifications, `DeleteUserNotificationsHandler` (the user's notifications, U8) | Yes; Notifications' declares the user |
| `DeleteIdentityAccountCommand` | `DeleteUserHandler` | ControlPlane, `DeleteIdentityAccountHandler` (calls the identity provider) | No |
| `DeleteUserFilesCommand` | `DeleteUserHandler` | ControlPlane, `DeleteUserFilesHandler` (deletes the prefixes `users/{userId}/` and `exports/users/{userId}/` in the file store) | No |
| `EraseFormerMemberCommand` | `DeleteUserHandler`, in each tenant where the user accepted an invitation | ControlPlane, `EraseFormerMemberHandler` | Yes, the tenant's |

1. The check. `ListUserMembershipsQuery` finds the user (404 `user.not_found`), refuses a system admin (409 `user.is_system_admin`) and lists the user's memberships, by tenant id. For each tenant the user owns that is active, suspended, closed or purging, `GetLastOwnershipQuery` asks the tenant's rule (`Tenant.CheckUserDeletion`, K1), without a lock. If the user is the last Owner of any, the answer is 409 `user.last_owner`, `tenantIds` names those tenants, and nothing changes.
2. The removals. For each membership, `RemoveUserMembershipCommand` locks the tenant row (K6), counts the Owners again under the lock, and removes the membership. The tenant's `RemoveForUserDeletion` asks the same rule again. If the user became the tenant's last Owner since the check, it changes nothing there and the request stops with 409 `user.last_owner` for that tenant. The tenants the user already left stay left; the user is not erased. In the same transaction, under the same lock, the tenant's invitations lose the user's address (A8, the same `Tenant.RemoveForUserDeletion`, which answers a `UserDeparture`): the invitations the user accepted, the invitations to the user's address, and the invitations to the address of an invitation the user accepted, in every state (`ITenantRepository.FindInvitationsOfUserAsync`). The last kind covers a person who joined with another of their verified addresses, and an earlier invitation that a new one to the same address replaced. The address of the user is read as a value, without a lock of the user (`IUserRepository.FindProfileAsync`, K6a); the step takes no new lock and keeps the lock order. A pending invitation always has an address (`ck_invitations_pending_has_email`), so a pending one among them, expired or not, is cancelled first, as a closure cancels it (K6h). Such an invitation exists when the user joined with another address: `member.exists` asks the members' stored addresses, and the acceptance cancels no other invitation. Its identity provider invitation is withdrawn after the commit (`WithdrawSignUpCommand`). The step writes no audit entry of its own: the user's deletion is audited (`member.removed`, `user.deleted`), and a closure's cancellations write none either. The summary is saved from the rows in the same save (R12). It keeps an Owner invitation's address only while the tenant has no Owner, and the step leaves every tenant with an Owner, because it refuses the last one; so no summary holds an erased address.
3. The erasure. `DeleteUser` locks the user row, declares the user and reads the memberships again. A membership that appeared since, such as an invitation accepted at the same moment, stops it with 409 `user.has_memberships`; a second deletion removes it. An acceptance locks the user's row (`FOR NO KEY UPDATE`, K6) and refuses a deleted user (403 `user.deleted`), so it either commits before this step reads the memberships or finds the user deleted. With none left, it lists the tenants where the user accepted an invitation, under the same lock (`IUserRepository.ListJoinedTenantsAsync`, R11's `own_accepted_invitations`). It then erases the email address, the name, the time zone and the reason of a suspension, which is personal data about the user (step 37b), sets `DeletedAt`, deletes the user's verification codes and the records of their stored files (`IUserRepository.DeleteOwnRecordsAsync`), and publishes `UserDeletedEvent`, `DeleteIdentityAccountCommand`, `DeleteUserFilesCommand` and one `EraseFormerMemberCommand` for each tenant it listed, in that tenant (`DeliveryOptions.TenantId`), in the same transaction. Each carries the user's address as it was before the erasure, or none for a user deleted before.
4. After the commit, `DeleteIdentityAccountHandler` deletes the user at the identity provider, with the retries of `ControlPlane:IdentityProvider:RetryDelays`, and `DeleteUserFilesHandler` deletes every file of the user (`ARCHITECTURE.md`, section 7, "File storage"). A file deletion that fails retries (W11), then waits in the dead letter queue, whose move logs the error that is the alarm: the deletion is not done until it succeeds (GDPR, Article 17). A second deletion of a deleted user answers 204, records nothing again, and asks the identity provider and the file store again.
5. The tenants the user left before (A8; the maintainer's decision of 2026-10-23, option B: a tenant the user left counts as a tenant they joined). After the commit, `EraseFormerMemberCommand` runs in each tenant step 3 listed, in that tenant's transaction (R4). It locks the tenant row (K6l) and applies the rule of step 2 without its membership part (`Tenant.EraseFormerMember`, which shares the erasure with `RemoveForUserDeletion`): the invitations the user accepted, the invitations to the user's address and to the address of an invitation the user accepted lose the address, and a pending one among them is cancelled first and its identity provider invitation withdrawn after the commit (`WithdrawSignUpCommand`). Example: Ayşe joined Acme by an invitation, Acme removed her and invited her again, and the platform deletes her a month later. Acme's accepted invitation loses her address, and the pending one is cancelled and loses it too. The list holds the tenants step 2 just left too: there the command finds the addresses erased and changes nothing, and a tenant that removed the user while the deletion ran is reached all the same. A tenant with no invitation of the user, a purged one included, saves nothing. A command that arrives twice finds nothing to cancel or erase. A membership in such a tenant is an error, because a deleted user is a member of no tenant. A tenant the user never joined keeps its invitations to the address: they go with that tenant's purge. The step writes no audit entry, as step 2's erasure writes none.
   It runs after the user's erasure, beside `DeleteIdentityAccountCommand`, for three reasons. A tenant's invitations change only in that tenant's transaction (R4), so the step cannot join step 3's transaction. The tenants are listed under the user's lock, which an acceptance also takes (K6f), so no tenant joins the list between the read and the erasure. And the identity provider's deletion keeps its place after step 3: no new step comes before it, so no failure of this step can keep the identity provider's account alive. The cost: the address waits in the message store until each command is handled, and a command that fails for good keeps it in the dead letter queue until its retention ends (W13), with the tenant's invitations not erased. A second deletion sends the commands again, without the address, which a deleted user no longer has; they still reach the invitations the user accepted and those to the addresses of these.

A deleted user is never a member and never an Owner (`ARCHITECTURE.md`, section 6, "Rules without an id", "Deleted user"). A deleted user is refused at the door until their session ends (A9), so they cannot accept an invitation meanwhile. A person who signs up again later, with the same address, is a new person: an invitation whose address was erased matches no verified address (`Invitation.CheckEmail`), so the preview refuses them with 403 `invitation.email_mismatch`. The acceptance answers such an invitation by its state before it compares the address: 404 `invitation.not_found` for a cancelled one, 409 `invitation.not_pending` for an accepted one. Tests: `DeleteUserTests` (`DeleteUser_AcceptedInvitationsInTwoTenants_ErasesTheirAddressesAndATenantNeverJoinedKeepsIt`, `DeleteUser_APendingInvitationToTheirAddressInATenantTheyJoined_CancelsItErasesItAndWithdrawsItsSignUp`, `DeleteUser_AnInvitationAcceptedInATenantTheyLeft_ErasesItsAddressesCancelsThePendingOneAndWithdrawsItsSignUp`, `EraseFormerMember_Twice_ChangesNothingMoreAndWithdrawsTheSignUpOnce`, `DeleteUser_AgainAfterAnEarlierDeletionLeftATenantTheyLeftWithTheAddress_ErasesItThere`, `StoreInvitation_PendingWithoutAnAddress_IsRefused`, `StoreInvitation_FinishedWithoutAnAddress_IsStored`), `GetInvitationPreview_AnInvitationWhoseAddressWasErased_IsForbiddenWithTheBodyAcceptingGives`, `PurgeTenant_AMemberLeftWithoutATenantWhoLeftAnotherTenantBefore_ErasesTheirAddressThere`, `DeleteUser_AnInvitationAcceptedInATenantTheyLeftOnAWebAndAWorkerHost_ErasesItAndWithdrawsItsSignUpInTheWorker`, `OwnAcceptedInvitationsPolicyTests`, `TenantTests`, `InvitationTests`.

Source: Kleppmann, Chapter 7, "Write Skew and Phantoms". Vernon, "Effective Aggregate Design". GDPR, Article 17.

- Notifications. `UserDeletedEvent` also deletes the user's notifications, in every bell, in a transaction of Notifications that declares the user (R4, U8; `notifications.md`, section 5). A copy deletes nothing more. A deleted user is told of nothing (U3). Another person's notification keeps the user by id only, so it needs no change: its read names them "Deleted user" in the reader's language (U2). The user's deletion removes their memberships without `MemberRemovedEvent`, so it sends no `member.removed`.

## 2. The user's own deletion

The user deletes their own account at once, after a fresh code to their address (the maintainer's decisions of 2026-11-03). It takes the steps of section 1, by the user. The screens: Figma, "6 · Settings › Account and security", 6.22 to 6.24.

| Message | Sent by | Handled by | Handler has a transaction |
| --- | --- | --- | --- |
| `GetMeQuery`, `ListUserMembershipsQuery`, `GetLastOwnershipQuery` | `POST /v1/me/account-deletion` and `.../confirm` | ControlPlane, as in section 1, step 1 | Yes |
| `RequestAccountDeletionCommand` | `POST /v1/me/account-deletion` | ControlPlane, `RequestAccountDeletionHandler` | Yes; it declares the user |
| `UserDeletionRequestedEvent` | `RequestAccountDeletionHandler` | Audit, `RecordUserDeletionRequestedHandler` (`user.deletion_requested`, platform log, by the user) | Yes |
| `VerificationCodeReadyEvent` | `RequestAccountDeletionHandler` | Notifications, `SendVerificationCodeEmailHandler` (the email `deletion-code`) | No |
| `ConfirmAccountDeletionCommand` | `POST /v1/me/account-deletion/confirm` | ControlPlane, `ConfirmAccountDeletionHandler` | Yes; it declares the user |
| `RemoveUserMembershipCommand`, `DeleteUserCommand` and their messages | the same endpoint, as in section 1 | as in section 1 | as in section 1 |
| `UserDeletionConfirmationReadyEvent` | `DeleteUserHandler`, when the user deleted themselves | Notifications, `SendUserDeletionConfirmationEmailHandler` (the email `account-deleted`) | No |

1. The request. The endpoint runs the check of section 1, step 1, for the user: a system admin is refused with 409 `user.is_system_admin`, because their admin rights go first, and a root system admin cannot be revoked at all (`flows/system-admins.md`); the last Owner of an active, suspended, closed or purging tenant gets 409 `user.last_owner`, whose `tenantIds` name those tenants, so the screen says "Make someone else an Owner, or close the organisation first." Then `RequestAccountDeletion` sends a code of six digits to the user's address and records `user.deletion_requested`. The code follows `ARCHITECTURE.md`, section 6, "Verification codes".
2. The confirmation. With the code, the endpoint runs the check again, then `ConfirmAccountDeletion` uses the code: a wrong, used or expired code answers 400 and deletes nothing. Then the endpoint sends the removals and `DeleteUserCommand` of section 1, steps 2 and 3, with the user as the actor. The audit entry `user.deleted` names the user as the one who acted.
3. The confirmation email. `DeleteUserHandler` sees that the user deleted themselves, because the actor is the user, and publishes `UserDeletionConfirmationReadyEvent` with the address the user had, read before the erasure. Notifications tells that address that the account was deleted, in the user's language (GDPR, Article 12(3)). The address waits in the message store until the event is handled (W13), as for `EraseFormerMemberCommand`. A system admin's deletion sends no such email.

Tests: `RequestAccountDeletionTests`, `ConfirmAccountDeletionTests`, `VerificationCodeTests`, `DeleteUserTests` (`DeleteUser_AUserWithFiles_DeletesTheirFilesAndTheirRecordsAndSendsNoConfirmation`), `SendVerificationCodeEmailHandlerTests`, `RecordUserDeletionRequestedTests` in Audit.
