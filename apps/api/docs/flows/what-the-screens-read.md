# What the screens read

This file is a flow of `ARCHITECTURE.md`, section 6. It says what happens, step by step. The rules it cites by id are in `ARCHITECTURE.md` and `api-catalog.md`.

The tenant web and the platform app read these fields and endpoints (api-catalog, step 20l). Each of them only reads.

- The member's tenant (`GetMyTenant`, `MyTenantDetailResponse`): the tenant, when it was created (`tenants.created_at`), the member's role, and the names of the role's permissions in ordinal order, from the role in code (`BuiltInRoles`) for a built-in role and from its rows of `role_permissions` for a custom role (A3). The document types each name as the schema `Permission` (N11), so a misspelt permission name in the web does not compile. The web shows an action only when the list holds its permission. The list is for the screen only: every endpoint still checks its own permission (A1, A5), so a list that is out of date never lets a request through. The handler reads the member's role from their membership in its own transaction. It also answers `planName`, `entitlements`, every key of the list with its effective value at the moment of the request (a feature `true` or `false`, a limit a number, `null` for unlimited), and `usage`, the tenant's count of each limit, so the web shows a limit and adds no list up (ARCHITECTURE.md, E3, E4; `plans-and-entitlements.md`). Settings › Roles reads its limit from `entitlements["roles.custom.max"]`.
- The platform's plans (`ListPlans`, `GetPlan`) and a tenant's plan (`GetTenantPlan`): each key's plan value, override (with its expiry, its state `active` or `expired`, the reason, who set it and when), effective value and count, and the previews before a change (`GetPlanUpdatePreview`, `GetTenantPlanChangePreview`) (`plans-and-entitlements.md`).
- `ListMyTenants` and `AcceptInvitation` answer the member's role in each tenant (`MyTenantResponse.role`). `ListMembers` and `ChangeMemberRole` answer `joinedAt` (`memberships.joined_at`). `ListInvitations`, `InviteMember` and `InviteOwner` answer `invitedByName`: `{ name, deleted }` of the inviter, as they are stored at the moment of the read, as the audit names are (K3); `invitedBy` stays. They answer `state` too: the handler reads it with `Invitation.StateAt` and the module's clock at the moment of the read, so a screen never derives it from `expiresAt` by the browser's clock. The list holds pending invitations only, so it is `pending` or `expired`; inviting answers `pending` (`ListInvitations_APendingInvitationAtItsExpiryByTheClock_TurnsFromPendingToExpired`). They answer `language` too: the language the invitation keeps for its email (K8), read from `invitations.language`, never the caller's. A client that invites the same person again can send it back in the request's `language`, so the new email speaks the language of the one it replaces. `ListTenants` and `GetTenant` answer the same field in `ownerInvitation`, from the tenant's summary (R12). The preview does not answer it: the invited person does not need it. `ListUsers`, `SuspendUser`, `ReactivateUser` and `RenameUser` answer `membershipCount` (R13) and `createdAt` (`users.created_at`). `ListTenants` and `GetTenant` answer `createdAt` too (`tenants.created_at`), for the Created column of the Organisations list and the Created row of an organisation's page (step r13). Every status keeps the column, a purged tenant's tombstone too (K4), so it is a read: no column was added. `TenantResponse`, the answer of the commands, does not carry it.
- The system admins' "Add" dialog finds a person by the whole email address: `ListUsers` with the filter `email` (step r13). The address takes its one form (`EmailAddress`) in the handler, and the query compares it with the stored address by plain equality, through the B-tree on `users.email`, with no `lower()`. A search with `q` would also find `kali@` for `ali@`, and the right person could fall off the first page. Addresses are not unique (the review of 2026-10-21), so the answer is a page of 0, 1 or more users. The filter combines with `isSystemAdmin`, `status` and `q`.
- The invitation preview (`GetInvitationPreview`, `POST /v1/me/invitations/preview`, body `{ code }`). The code is the invitation's secret, so it travels in the body: a URL ends up in access logs, in the browser's history and in `Referer` headers. The preview finds the invitation as accepting does (W3, T2): the tenant of the code is declared, then the invitation is found by the hash of the secret, and row level security hides another tenant's invitation. The order of the answers is:
  1. A missing, empty or blank code: 400 `invitation.code_required`. A body the endpoint cannot read: 400 `request.invalid`.
  2. A code that does not parse, an unknown tenant or an unknown secret: 404 `invitation.not_found`, the body accepting gives, so a code cannot be probed.
  3. No verified email address of the caller is the invited one: 403 `invitation.email_mismatch`, the body accepting gives, for every state of the invitation. The verified addresses come from the identity provider's server, as for accepting. The body holds no address. So a person who holds a forwarded link learns only what the email told them (the maintainer's decision in step 20l).
  4. Else 200 `{ tenantName, inviterName, role, expiresAt, state }`.
- `inviterName` is `{ kind, name, deleted }`. `kind` is `platform`, with no name and no `deleted`, when a system admin invited: the system admin list holds the inviter. So the screen never shows a system admin's name. `state` is `pending`, `expired` (pending past its expiry, read at the moment of the request), `accepted` or `cancelled` (`Invitation.StateAt`). The preview answers the state of a cancelled invitation, where accepting answers 404: only the invited person sees it. An invitation of a suspended tenant answers `pending`; accepting it then answers 409 `tenant.suspended` (`GetInvitationPreview_AnInvitationOfASuspendedTenant_IsPending`).
- The preview shares accepting's rate limit, because a guessed code also costs a call to the identity provider (API4). It changes nothing, publishes nothing and writes no audit entry (K3). The me door refuses a suspended or a deleted user (A9).
- The user detail (`GetUser`, `GET /v1/platform/users/{userId}`, `platform.users.read`): the user as in the list, `suspendedAt`, `suspendedBy` and `memberships`. `suspendedBy` holds the names of the system admin who suspended the user: `SuspendUser` writes `users.suspended_by`, and `ReactivateUser` clears it. The memberships are under row level security, so the handler declares the user (R11), as a user's deletion does. One query reads them, with their tenants and roles joined, by the tenant's name, then id. `lastOwner` is true when the user's role holds `tenant.owners.manage` (A1) in a tenant whose summary counts one Owner (R12): the user's own memberships show no other member.
- The platform's 37b frames (step 37b): the tabs of the Organisations and Users lists read `statusCounts` and send `status` once for each status of a tab (the Organisations tab Closed sends `closed` and `purging`; All sends every status but `purged`). A row of the tenant list reads `plan` and `pendingInvitationCount`. The organisation's page reads `createdBy`, `suspendedAt`, `suspendedBy`, `closedBy`, `purgeStartedAt`, `pendingInvitationCount` and the Owner invitation's `sentAt`; a null value shows no "by" part, or no row. The user's page reads `suspensionReason` and `systemAdminGrantedBy`. The suspend dialog of a user sends `{ reason }`.
- The screens of the audit retention (step 37c; `ARCHITECTURE.md`, E4, K14, K15). The plan editor's impact dialog (6.19) reads `retentionShortened` of `GetPlanUpdatePreview`: `{ count, fromDays, toDays }`, the organisations on the plan whose period gets shorter, those without an override of the key that has not expired, and the plan's period before and after; null when the edit keeps the period as long or longer. The count is the whole edit's: no search or page of the preview narrows it. The Change plan dialog (4.15) reads `retentionShortened` of `GetTenantPlanChangePreview`: `{ fromDays, toDays }` under the organisation's overrides, or null. `fromDays` is null for no limit. The override dialogs (4.16, 4.17, 4.49) read `GetTenantPlan`: the plan's value and name, the override's value and its expiry; a shorter period is the comparison of the two values, and the hold's 30 days are `AuditRetention.Grace` of `@repo/api-client`. 4.49's sentence of an expiry needs no other field: the expiry is the date the admin enters, and the plan's value and name are in `GetTenantPlan`. The organisation's Activity log (12.01 to 12.11) reads `GetAuditRetention`, `GET /v1/tenants/{tenantId}/audit-log/retention`, with `tenant.audit.read`: `days`, null for no limit, and `shortening`, `{ days, goesAt }` while a hold runs and an entry that the hold keeps is older than the period, else null. The platform's Activity log (7.01, 7.08) reads `GetPlatformAuditRetention`, `GET /v1/platform/audit-log/retention`, with `platform.audit.read`: `{ days }`, the setting `Audit:Retention:Days`.
- The screens of the terms of use (step 38; `flows/terms-of-use.md`). The platform's Settings › Terms of use (11.01 to 11.15) reads `GetTermsOfUse`: each version's `effectiveDate`, `url`, `summary`, `state` for the pill, `requiresAcceptance`, `acceptedCount` and the list's `activeUserCount` for "18 of 67 accepted", and `locked`, which disables the link and `requiresAcceptance` in 11.10 with their reason. Add version is disabled while a version's `state` is `scheduled`. A version's page reads `GetTermsVersion` and `ListTermsVersionPeople` with `status=accepted` or `status=not_yet`, each person's `name`, `email` and `acceptedAt`. The web's gate after sign-in (1.09 to 1.12, 1.14) and Home's notice (4.03) read `GetMyTerms`: `action` and the version's `effectiveDate`, `url` and `summary`. Accept invitation (1.15) reads the version in force from `GetTermsInForce` and sends its `id` as `termsVersionId`; the entry pages' "Terms" link reads the same, and a 204 hides it.
- Which date each screen shows. The Banner of 12.10 shows `goesAt`, the end of the hold that the daily job keeps. After a plan change or an override, it is the event's moment plus 30 days, the same date as the Owners' `tenant.plan_changed`, which names `retentionDays` and `retentionGoesAt` from the event (`notifications.md`). After a plan edit or an expiry, which have no event for the organisation, the hold starts at the job's next run, up to a day later; until then the Banner shows the date the job would keep if it ran at the moment of the read, so the date shown is at most a day earlier than the job's, never later, and moves to the job's date once the job has run. The job deletes the held entries at its first run after `goesAt`, at most a day later (K14). The dialogs of the platform (4.15, 4.16, 4.17, 4.49, 6.19) show no date: they say "30 days", from the moment of the change.
- Each list is one query for its page, and one for its total: the new fields are on the rows that the page reads, or on a row that it joins (the role, the inviter's user, the tenant's plan and summary). `ListTenants` and `ListUsers` read a third query, the count of each status over every row, without the search or any filter (the maintainer's decision of 2026-11-10); a test sends the list with and without a status filter and counts the same SQL commands. A test sends a page of one item and a page of three, and counts the SQL commands of each request (`SqlCommands`, `ARCHITECTURE.md`, section 9): a longer page sends no more.
- Tests: `GetMyTenantTests`, `ListMyTenantsTests`, `ListMembersTests`, `ListInvitationsTests`, `InviteMemberTests`, `InviteOwnerTests`, `GetInvitationPreviewTests`, `ListUsersTests`, `GetUserTests`, `ListTenantsTests`, `GetTenantTests`, `GetPlanUpdatePreviewTests`, `GetTenantPlanChangePreviewTests`, `GetAuditRetentionTests`, `GetPlatformAuditRetentionTests`.

Source: OWASP API Security Top 10, API1 and API3. GDPR, Article 5(1)(c) (data minimisation). RFC 9110, section 17.9 (sensitive information in URIs).
