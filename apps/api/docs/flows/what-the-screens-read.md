# What the screens read

This file is a flow of `ARCHITECTURE.md`, section 6. It says what happens, step by step. The rules it cites by id are in `ARCHITECTURE.md` and `api-catalog.md`.

The tenant web and the platform app read these fields and endpoints (api-catalog, step 20l). Each of them only reads.

- The member's tenant (`GetMyTenant`, `MyTenantDetailResponse`): the tenant, when it was created (`tenants.created_at`), the member's role, and the names of the role's permissions in ordinal order, from the role in code (`BuiltInRoles`) for a built-in role and from its rows of `role_permissions` for a custom role (A3). The document types each name as the schema `Permission` (N11), so a misspelt permission name in the web does not compile. The web shows an action only when the list holds its permission. The list is for the screen only: every endpoint still checks its own permission (A1, A5), so a list that is out of date never lets a request through. The handler reads the member's role from their membership in its own transaction. It also answers `planName`, `entitlements`, every key of the list with its effective value at the moment of the request (a feature `true` or `false`, a limit a number, `null` for unlimited), and `usage`, the tenant's count of each limit, so the web shows a limit and adds no list up (ARCHITECTURE.md, E3, E4; `plans-and-entitlements.md`). Settings › Roles reads its limit from `entitlements["roles.custom.max"]`.
- The platform's plans (`ListPlans`, `GetPlan`) and a tenant's plan (`GetTenantPlan`): each key's plan value, override (with its expiry, its state `active` or `expired`, the reason, who set it and when), effective value and count, and the previews before a change (`GetPlanUpdatePreview`, `GetTenantPlanChangePreview`) (`plans-and-entitlements.md`).
- `ListMyTenants` and `AcceptInvitation` answer the member's role in each tenant (`MyTenantResponse.role`). `ListMembers` and `ChangeMemberRole` answer `joinedAt` (`memberships.joined_at`). `ListInvitations`, `InviteMember` and `InviteOwner` answer `invitedByName`: `{ firstName, lastName, deleted }` of the inviter, as they are stored at the moment of the read, as the audit names are (K3); `invitedBy` stays. They answer `state` too: the handler reads it with `Invitation.StateAt` and the module's clock at the moment of the read, so a screen never derives it from `expiresAt` by the browser's clock. The list holds pending invitations only, so it is `pending` or `expired`; inviting answers `pending` (`ListInvitations_APendingInvitationAtItsExpiryByTheClock_TurnsFromPendingToExpired`). They answer `language` too: the language the invitation keeps for its email (K8), read from `invitations.language`, never the caller's. A client that invites the same person again can send it back in the request's `language`, so the new email speaks the language of the one it replaces. `ListTenants` and `GetTenant` answer the same field in `ownerInvitation`, from the tenant's summary (R12). The preview does not answer it: the invited person does not need it. `ListUsers`, `SuspendUser`, `ReactivateUser` and `RenameUser` answer `membershipCount` (R13) and `createdAt` (`users.created_at`). `ListTenants` and `GetTenant` answer `createdAt` too (`tenants.created_at`), for the Created column of the Organisations list and the Created row of an organisation's page (step r13). Every status keeps the column, a purged tenant's tombstone too (K4), so it is a read: no column was added. `TenantResponse`, the answer of the commands, does not carry it.
- The system admins' "Add" dialog finds a person by the whole email address: `ListUsers` with the filter `email` (step r13). The address takes its one form (`EmailAddress`) in the handler, and the query compares it with the stored address by plain equality, through the B-tree on `users.email`, with no `lower()`. A search with `q` would also find `kali@` for `ali@`, and the right person could fall off the first page. Addresses are not unique (the review of 2026-10-21), so the answer is a page of 0, 1 or more users. The filter combines with `isSystemAdmin`, `status` and `q`.
- The invitation preview (`GetInvitationPreview`, `POST /v1/me/invitations/preview`, body `{ code }`). The code is the invitation's secret, so it travels in the body: a URL ends up in access logs, in the browser's history and in `Referer` headers. The preview finds the invitation as accepting does (W3, T2): the tenant of the code is declared, then the invitation is found by the hash of the secret, and row level security hides another tenant's invitation. The order of the answers is:
  1. A missing, empty or blank code: 400 `invitation.code_required`. A body the endpoint cannot read: 400 `request.invalid`.
  2. A code that does not parse, an unknown tenant or an unknown secret: 404 `invitation.not_found`, the body accepting gives, so a code cannot be probed.
  3. No verified email address of the caller is the invited one: 403 `invitation.email_mismatch`, the body accepting gives, for every state of the invitation. The verified addresses come from the identity provider's server, as for accepting. The body holds no address. So a person who holds a forwarded link learns only what the email told them (the maintainer's decision in step 20l).
  4. Else 200 `{ tenantName, inviterName, role, expiresAt, state }`.
- `inviterName` is `{ kind, firstName, lastName, deleted }`. `kind` is `platform`, with no names and no `deleted`, when a system admin invited: the system admin list holds the inviter. So the screen never shows a system admin's name. `state` is `pending`, `expired` (pending past its expiry, read at the moment of the request), `accepted` or `cancelled` (`Invitation.StateAt`). The preview answers the state of a cancelled invitation, where accepting answers 404: only the invited person sees it. An invitation of a suspended tenant answers `pending`; accepting it then answers 409 `tenant.suspended` (`GetInvitationPreview_AnInvitationOfASuspendedTenant_IsPending`).
- The preview shares accepting's rate limit, because a guessed code also costs a call to the identity provider (API4). It changes nothing, publishes nothing and writes no audit entry (K3). The me door refuses a suspended or a deleted user (A9).
- The user detail (`GetUser`, `GET /v1/platform/users/{userId}`, `platform.users.read`): the user as in the list, `suspendedAt`, `suspendedBy` and `memberships`. `suspendedBy` holds the names of the system admin who suspended the user: `SuspendUser` writes `users.suspended_by`, and `ReactivateUser` clears it. The memberships are under row level security, so the handler declares the user (R11), as a user's deletion does. One query reads them, with their tenants and roles joined, by the tenant's name, then id. `lastOwner` is true when the user's role holds `tenant.owners.manage` (A1) in a tenant whose summary counts one Owner (R12): the user's own memberships show no other member.
- Each list is one query for its page, and one for its total: the new fields are on the rows that the page reads, or on a row that it joins (the role, the inviter's user). A test sends a page of one item and a page of three, and counts the SQL commands of each request (`SqlCommands`, `ARCHITECTURE.md`, section 9): a longer page sends no more.
- Tests: `GetMyTenantTests`, `ListMyTenantsTests`, `ListMembersTests`, `ListInvitationsTests`, `InviteMemberTests`, `InviteOwnerTests`, `GetInvitationPreviewTests`, `ListUsersTests`, `GetUserTests`, `ListTenantsTests`, `GetTenantTests`.

Source: OWASP API Security Top 10, API1 and API3. GDPR, Article 5(1)(c) (data minimisation). RFC 9110, section 17.9 (sensitive information in URIs).
