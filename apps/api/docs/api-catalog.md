# API catalog

The endpoints of the template's core API when it is complete. Each row says who may call it, the audit entry it writes, the notification it sends, the external system it reaches, and the step that builds it. Code follows this catalog. A change to an endpoint changes this file in the same pull request.

With step 20l the API part of the designed screens is complete: the tenant web and the platform app read every field and endpoint they show. The web app is the next step.

Status: **has** (exists, unchanged), **changes** (exists, changes), **new**.
Audit: **T** = the tenant's audit log, **P** = the platform audit log.

## 1. Me: `/v1/me`

The signed-in user, acting for themselves. No permission; the user reaches only their own data (N6).

- `GetMe` has no status. A suspended user gets 403 `user.suspended` on every `me` endpoint, and a deleted user 403 `user.deleted` (A9), so the status would always be "active".
- A person becomes a user only through an invitation or as a root system admin at the system door (`flows/system-admins.md`). `GetMe` answers a signed-in person who is not a user yet with 404 `user.not_found`. The web shows "no access yet".
- A user's preferences are their `language`, one of the `Language` list (`en`, `tr`, `ar`), and their `timeZone`, an IANA name such as `Europe/Dublin`, or null for "not set": the web then uses the browser's time zone. They follow the user to every tenant and device. A new user starts with the language of the invitation they accept; a root system admin who enters first through the system door starts with `en` (K8).

## 2. Tenant: `/v1/tenants/{tenantId}`

A member of the tenant. Each endpoint names a permission. To a non-member the tenant does not exist (T3).

- The tenant's name is locked in the tenant app: only the platform renames a tenant (`RenameTenant`, platform). The tenant path has no `PATCH /v1/tenants/{tenantId}` and no `tenant.profile.update` (the maintainer's decision in step 20h).
- A member of a suspended tenant gets 403 `tenant.suspended`, and a member of a closed one 403 `tenant.closed`, at the door and again under the tenant's lock in every command (K6). A non-member gets 404 `tenant.not_found` (T3).

- A request gives a role by its id (`roleId`), never by a name: `InviteMember` and `ChangeMemberRole` (step r4b). A response that holds a role answers `RoleResponse`, `{ id, name, builtIn }` (K5). A tenant has its built-in roles (Owner, Admin, Member) and the custom roles it builds from the tenant pool (ARCHITECTURE.md, A3; `flows/custom-roles.md`).
- Every operation on a role follows one rule against privilege escalation: the actor's role holds every permission of the role it acts on, and of the member's or the invitation's current role (403 `role.escalation`; the maintainer's decision 2 in step r4b). It applies to `CreateRole`, `UpdateRole` (before and after), `DeleteRole`, `InviteMember`, `ChangeMemberRole`, `RemoveMember` and `RevokeInvitation`. An Owner holds every permission, so it never limits an Owner. Source: Kubernetes RBAC, "Privilege escalation prevention".
- `InviteMember`, `ListInvitations` and the platform's `InviteOwner` answer `InvitationResponse`, with `invitedByName`, `state`, `pending` or `expired`, and `language`, the language the invitation keeps (K8) (`flows/what-the-screens-read.md`). `ListMembers` and `ChangeMemberRole` answer `MemberResponse`, with `joinedAt` (step 20l).
- `ListMembers` answers `deleted` for each member, as the audit logs do. A system admin's deletion takes the user out of every tenant first (A8), so a deletion leaves no member with `deleted: true`. The screen shows "Deleted user", as for audit (K3).

## 3. Platform: `/v1/platform`

A system admin with a second factor (A6). Every action writes to the platform audit log. The provider's app is "Platform" on screen, because "Admin" is a role in the tenant web (the maintainer's decision in step 20k). The person keeps the name "system admin".

- `ListTenants` and `GetTenant` read the tenant's summary (R12), which every command that changes a membership or an invitation writes under the tenant's lock: `memberCount`, `ownerCount`, and, while `ownerCount` is 0, `ownerInvitation`, the latest Owner invitation, `{ email, expiresAt, state, language }`, with `state` `pending`, `expired` (read from `expiresAt` at the moment of the request) or `cancelled`, never `accepted`; null when there is none, and null when `ownerCount` is more than 0. `reopenableUntil` is `closedAt` plus `ControlPlane:Tenants:ReopenPeriod` for a closed tenant, else null. `GetTenant` also answers `purgeWarningAt`, when the Owners are, or were, warned of the purge: `closedAt` plus `ControlPlane:Tenants:ReopenPeriod` less `ControlPlane:Tenants:PurgeWarningLead`, for a closed or a purging tenant, else null. It is computed on read, never stored (step r12); the warning's audit entries carry the same moment.
- A list item names no Owner; it counts them in `ownerCount` (the maintainer's decision in step r2a). `GetTenant` answers `owners`, every Owner in the order they joined. The page is one query; the total is a second query, as for every list. No query runs for each tenant.
- `ListUsers`, `GetUser`, `SuspendUser`, `ReactivateUser`, `RenameUser` and `GrantSystemAdmin` answer `isSystemAdmin` and `isRootSystemAdmin` for each user (step r5), and `systemAdminGrantedAt`, the grant's `grantedAt`, or null for a user who is no system admin (step r12). A root system admin is a system admin whose address `ControlPlane:SystemAdmins:RootEmails` names, read from the list on each request; nothing stores it. A user who is no system admin is never a root. The platform hides "Revoke" for a root (`flows/system-admins.md`). A root who has never entered the system door has no grant yet, so `isSystemAdmin` is false for them and the filter `isSystemAdmin=true` does not list them; their first entry grants them (step r12).
- `GrantSystemAdmin` and `RevokeSystemAdmin` ask for a fresh second factor: verified less than `ControlPlane:SystemAdmins:ReverificationWindow` ago (10 minutes by default). An older one, or none, answers 403 `system_admin.reverification_required` and nothing more, so the platform asks the person to verify again and retries. The door checks it before the endpoint runs, so a refused grant claims no Idempotency-Key and the same key works after the reverification (A6, step r12).
- The system door writes `system_admin.granted` in the platform's log, by the platform, when a root system admin enters it for the first time with a second factor, on any platform endpoint. That entry belongs to no endpoint's row (K3).

## 4. How audit and notifications connect

ControlPlane changes its data and writes an event to the outbox in the same transaction. Audit and Notifications take the event from their own queues. An endpoint never writes an email or an audit entry itself. When one event gives an entry in both logs, Audit writes both in one transaction.

- `SuspendTenant` → ControlPlane (state and event) → `TenantSuspendedEvent` → Audit: platform log "Ayşe Yılmaz suspended Acme", with the reason, and Acme's log "The platform suspended this tenant", without it.
- `CreateTenant` → ControlPlane (the tenant, its summary, the Owner invitation, the event and the command, in one transaction) → `TenantCreatedEvent` → Audit: both logs. Then every invitation's path: `OpenSignUpCommand` → Clerk → `RecordSignUpCommand` → `InvitationReadyEvent` → Notifications → Resend.
- `InviteMember` → ControlPlane (invitation, event and command) → `MemberInvitedEvent` → Audit: tenant log. `OpenSignUpCommand` → ControlPlane → Clerk: an invitation for an address without an account → `RecordSignUpCommand` → ControlPlane records Clerk's invitation → `InvitationReadyEvent` → Notifications → Resend: the invitation email with Clerk's link. Each message after the event has one handler, so its retries may be scheduled (W5).
- `InviteOwner` → ControlPlane (the replaced invitation cancelled, the new one, the event and the commands) → `OwnerInvitedEvent` → Audit: both logs. Then every invitation's path: `OpenSignUpCommand` → Clerk → `RecordSignUpCommand` → `InvitationReadyEvent` → Notifications → Resend; `WithdrawSignUpCommand` → Clerk withdraws the replaced invitation's. Every invitation email has the same text.

- A command that notifies → ControlPlane (state and event) → its event → Notifications: the handler of its notification type names the recipients and sends one `DeliverNotificationCommand` for each → the dispatcher writes the in-app notification in the recipient's transaction, and sends the generic email when the type is required or the recipient's preferences allow it (`SendNotificationEmailCommand` → Resend) → the commit signals the recipient's bell on the live channel (Valkey) → every web process writes the signal to that user's open streams (`flows/notifications.md`). The Notification column names each type and its recipients. Nobody is told of their own action.

## 5. Decided rules

### K1. Roles

- An Owner and an Admin invite members, change roles and remove members.
- Only an Owner gives or takes the Owner role. Only an Owner removes an Owner.
- A tenant always has at least one Owner. The last Owner cannot be removed or lose the role. So a tenant has no Owner only while its first Owner has not accepted: it is active, has no member, and its Owner invitation is pending, expired or cancelled. The platform invites an Owner then (K9). The platform can also make a member an Owner, with or without an Owner there (K13).
- A member cannot leave a tenant by themselves. An Owner or an Admin removes them. A member cannot remove themselves.
- A member may change their own role under the same rules. An Owner may step down when another Owner exists. An Admin may become a Member. An Admin cannot become an Owner.
- The Owner count includes every Owner membership. A system admin's deletion of a user removes the user's memberships first, and refuses the last Owner of an active, suspended or closed tenant, also when the user becomes it while the deletion runs (A8). So no deleted user is an Owner.
- Setting the role a member already has answers 200 and publishes nothing, so it writes no audit entry (I1).
- A removed member loses access at once: the tenant door reads the membership on every request (T7). No cache is added.
- These rules live in Domain, on the tenant (`Tenant.ChangeRole`, `Tenant.Remove`), because "at least one Owner" is the tenant's rule (M1). A permission says who passes the door; a Domain rule says what can happen to an Owner.
- A tenant builds custom roles from the tenant pool (ARCHITECTURE.md, A3). Of the built-in roles, only the Owner creates, changes and deletes one (`tenant.roles.create`, `tenant.roles.update`, `tenant.roles.delete`); the permissions are not owner-only, so an Owner may give them to a custom role. Every built-in role that invites or changes a member's role reads the roles (`tenant.roles.read`). A custom role never holds `tenant.owners.manage`. Sources: GitHub, "Custom repository roles" (organization owners create them); GitLab.com, "Custom roles" (the group's Owner). (The maintainer's decision 1 in step r4b.)
- Nobody acts on a role stronger than their own (the escalation rule, section 2 of this catalog): the actor's role holds every permission of the role an operation gives, takes, changes or deletes, and of the member's or the invitation's current role. The Owner rules above stay as they are and come first, so an Admin who acts on an Owner still gets `member.owner_requires_owner` or `invitation.owner_requires_owner`. The rule is `Role.CheckEscalation`, in Domain. Source: Kubernetes RBAC, "Privilege escalation prevention".
- A tenant has at most `roles.custom.max` custom roles, its effective value: the plan's value, overlaid by an override that has not expired (20 on Pro, 0 on Free); the built-in roles do not count (409 `plan.limit_reached`, with `entitlement` `roles.custom.max`). `Tenant.CreateRole` takes the effective entitlements, which the handler reads under the tenant's lock (ARCHITECTURE.md, E4, E6). With `roles.custom` off, a custom role is not created, edited, given to a member or named in a new invitation (403 `plan.feature_unavailable`); listing and deleting stay allowed, and a member who holds one keeps its permissions (E5).
- Each rule of the Owners asks for the permission `tenant.owners.manage`, never for the Owner role (ARCHITECTURE.md, A1). Only the Owner role holds it. An Owner is a member whose role holds it, and "at least one Owner" is at least one such member. Each tenant has its own Owner, Admin and Member roles (A2).
- Every command that changes the tenant, a membership or an invitation locks the tenant row first (K6).

### K2. Invitations

- A new invitation to an email with a pending invitation in the same tenant replaces it. The old link stops working at once. The emails are compared in their one form: trimmed and in lower case (ARCHITECTURE.md, section 6, "Rules without an id"). The API answers the address in that form.
- A replaced or a revoked invitation becomes `Cancelled`. Accepting it answers 404 `invitation.not_found`. There is no other status.
- A replacement is one command and one audit entry: `member.invited`, with the replaced invitation's id in its details. It writes no `invitation.revoked` entry (K3).
- "Send again" is not an endpoint of its own.
- An invitation lives `ControlPlane:Invitations:Lifetime`, at least one day. The email says the moment the link stops working, in the inviter's time zone (`flows/invitations.md`).
- An invitation keeps the language of its email (K8).
- The platform's Owner invitation follows K9. A member never invites into a tenant without an Owner, because such a tenant has no member.
- A tenant has at most one pending invitation to an email. A partial unique index on the tenant and the stored `email` of pending invitations keeps it. The tenant row lock is the first guard; the index is the second (K6).
- Each tenant may create `ControlPlane:Invitations:DailyLimitPerTenant` invitations in a rolling window of `InviteMemberHandler.LimitWindow`. The window counts every invitation the tenant created in it, cancelled and replaced ones included, so a replacement does not get around it. Over the limit, `InviteMember` answers 429 `invitation.daily_limit_reached` (RFC 6585), without a `Retry-After` header. It may become a platform setting later.
- An email that already belongs to a member, in ControlPlane and compared in its one form, answers 409 `member.exists`.
- The invitation email has the retries of the owner invitation email. After the last try the message goes to the dead letter queue. The invitation stays pending; the inviter can invite again, which replaces it.
- Closing a tenant cancels its pending invitations, in the same transaction. Accepting one then answers 404 `invitation.not_found`, as a revoked one, also after a reopening. An invitation to a suspended tenant cannot be accepted (409).

### K3. Audit

- Every command that changes state writes one audit entry in each log it belongs to. An architecture test enforces it. Reads write nothing. A change of a user's read state of their notifications writes nothing either: it is the reader's own view, not a change of the product's data (U7).
- An audit entry stores no personal name or email address. It stores the actor's user id, the target's kind and id, and the target's name only when the target is not a person. A tenant's name stays in the entry.
- A `member.invited` entry stores the invitation id, not the email address.
- The Audit column of the endpoint tables lists every operation. It is the specification. `AuditOperations` in `Audit.Domain` declares each operation once, and every Audit handler names its operation from it. The OpenAPI document publishes them as the schema `AuditOperation`, the type of `operation` in both logs. `AuditOperationTests` fails when the column and the class differ. A stored operation never changes.
- A role in the details of an entry is the role as it was at that moment: its name, its id and whether it is built in. ControlPlane's events carry all three, and Audit records them. The answer gives it as `AuditRoleResponse`, `{ id, name, builtIn }`: the role may be renamed or deleted since, so the entry is its own record of it. An entry written before step r4b keeps the name only (`owner`, `admin` or `member`): its `id` is null and `builtIn` is true (the maintainer's decision in step r4b).
- A change to a custom role writes `role.created`, `role.updated` or `role.deleted` in the tenant's log. The target is the role, with its name at that moment, because a role is not a person. `role.created` keeps the permissions, `role.updated` the old and the new name and the permissions added and removed.
- The details of an entry are one shape for each operation that keeps some, or null. `AuditDetailsTypes` in `Audit.Application` decides it for every operation, and the table of K3 in ARCHITECTURE.md, section 6, names each operation's type. The answer's `details` is that shape, with the operation as its discriminator, so a client narrows it by `operation` (`flows/reading-the-audit-logs.md`).
- The read side resolves names in one batch through an interface in `ControlPlane.Contracts` (API composition). Audit never reads `control_plane` tables directly.
- When a system admin deletes a user, `DeleteUser` erases the user's email address and names, so the read side gives the user no name and marks them deleted, and the screen shows "Deleted user". No audit entry changes, and the entry stays (GDPR Article 17).
- Every action of a system admin goes to the platform log. When it changes a tenant, it also goes to that tenant's log, with "Platform" in place of the person. In the tenant log, a system admin's action has the actor kind "platform" and no actor id.
- Nothing comes from Clerk: the API has no webhook.
- The platform log is a table of its own. The row level security of the tenant table does not change.
- The code, the table and the endpoint say `audit`. The screen label is "Activity".
- Sources: GDPR Articles 4(5) and 25 (pseudonymisation). Richardson, *Microservices Patterns*, "API composition".

### K4. Tenant lifecycle

- active ⇄ suspended → closed → purging → purged. A tenant is active from its creation, in one transaction (`flows/tenant-creation.md`); a creation that fails leaves no tenant. Active and suspended both go to closed, and a reopening goes closed → active.
- A suspension has a reason. Today it is text the system admin writes: 1 to 500 characters, trimmed. It holds no personal data, because the platform's log keeps it after the tenant's purge (ARCHITECTURE.md, A8). The platform side shows it (`GetTenant`, `ListTenants`); a member never sees it, and only the platform's audit entry holds it. Reactivating and reopening clear it. A billing reason comes with billing.
- closed: members cannot enter (403 `tenant.closed`), the data stays, and closing cancels the pending invitations. The tenant can be reopened while `closedAt` plus `ControlPlane:Tenants:ReopenPeriod` is in the future. The closure schedules two messages: the warning email to the Owners at `closedAt` plus the reopen period less `ControlPlane:Tenants:PurgeWarningLead` (7 days), and the purge at `closedAt` plus the reopen period. A reopening cancels neither: each acts only for a tenant still closed at its closure (`flows/tenant-purge.md`).
- purging: the purge has started, the pivot of the tenant purge. The tenant cannot be reopened (409 `tenant.not_closed`), and its members are refused as a closed tenant's (403 `tenant.closed`) until the purge's last step takes their memberships away. Every other platform command answers 409 `tenant.not_active`.
- purged: the tenant row is a tombstone. It keeps `id`, `name`, `slug`, `status`, `createdAt` and `purgedAt`; every module's data of the tenant is gone, and so is its Activity log. The platform's log keeps its entries about the tenant, with `tenant.purged`. The slug is never given again. A user the purge left without a tenant, who is not a system admin, is deleted by the platform. `ListTenants` and `GetTenant` show the tombstone with no member, no Owner and no Owner invitation.
- Only the platform renames a tenant (`RenameTenant`, platform). The tenant's name is locked in the tenant app.
- The slug never changes.
- An export of a tenant's data before its purge is not in this catalog.
- The billing state is not copied into the tenant's state. The tenant only reacts to a subscription event.

### K5. Contract

- An endpoint that creates a resource takes `Idempotency-Key`. One that sets a state does not (I1). An endpoint that takes the key answers 201 with its body (RFC 9110, section 15.3.2). A test fails for one that does not declare 201 (`OpenApiContractTests`).
- A 201 sends `Location` only where a GET reads the new resource: `CreateTenant`, with `/v1/platform/tenants/{tenantId}`, the route of `GetTenant` (RFC 9110, section 10.2.2). The API has no GET for one invitation, so `InviteMember` and `InviteOwner` send none, and their description says so: the target URI then identifies the resource (RFC 9110, section 15.3.2).
- A replayed answer carries `Idempotent-Replayed: true` (I5). The document declares the header on each answer an idempotent operation can replay.
- Every error answer is Problem Details (RFC 9457) with a `code`. A client shows its own text from `code`, never from `detail`, which stays English for developers and logs. The API sends no error text in another language.
- Every code has the form `area.reason`, in lower snake case: `tenant.not_found`. A test enforces it.
- One concept has one area and one word (ARCHITECTURE.md, section 10). A member's code is `member.*`, never `membership.*`: `member.last_owner`, `member.not_found`. A system admin's code says `system_admin`, never `staff`: `invitation.system_admin_cannot_join`. A test fails for a code in the area `membership` or with `staff` in it.
- Error codes are one enum in the OpenAPI document, the schema `ErrorCode`, for every operation. No client writes them by hand. Each owner declares its codes in one static class whose name ends with `ErrorCodes`: `PagingErrorCodes` in `SharedKernel`, `HostErrorCodes` in the host, and each module's in its Domain project (`ControlPlaneErrorCodes`). An `Error` takes an `ErrorCode`, only such a class declares one (`ErrorCode.Declare`), and each code has one declaration. The document lists every declared code, and only `Api/ErrorHandling/Problems.cs` writes the code member of an answer. `ErrorCodeTests` and `OpenApiContractTests` enforce it. The shared kernel stays free of module concepts (Evans, Chapter 14). Answers no endpoint gives have codes of their own: `auth.unauthenticated` (401), `auth.forbidden` (403 without a refusal), `rate_limit.exceeded` (429 of the rate limiter), `request.invalid` (a body or a value the endpoint cannot read), `request.validation_failed`, `route.not_found`, `route.method_not_allowed`, `request.unsupported_media_type`, `request.too_large`, `request.timeout` and `server.error`.
- A validation answer keeps `errors`: each field, by its command property in camel case, which is the request's JSON name, lists field codes, the schema `FieldErrorCode`: `required`, `email_invalid`, `too_long`, `time_zone_invalid`, `slug_invalid`. Each validator rule states its field code; a test fails for a rule without one.
- A field that holds a language is the one schema `Language` (K8). Its values are the tags. An unknown tag, a list of tags, a tag with spaces or a number is a body the endpoint cannot read, so it answers 400 `request.invalid`, as an unknown role does (the maintainer's decision in step 20j).
- An error answer may name tenants in `tenantIds`, when a client needs them to act: `user.last_owner` names the tenants where the user is the last Owner. Every other answer leaves it out. An answer about a key of the plans names it in `entitlement`: `plan.feature_unavailable`, `plan.limit_reached` and `plan.entitlement_invalid` (ARCHITECTURE.md, E1 to E5).
- The tenant door answers a stranger with the handlers' own `tenant.not_found`, so its body is the same apart from the trace id (T3, `TenantNotFoundTests`).
- 401 and 429 are declared on every operation. Every operation also declares Problem Details as its `default` answer, for a status it does not list, such as 405, 408, 413, 415 or 500. A test enforces both.
- Each operation that the rate limiter covers declares `Retry-After` on its 429: an integer, the seconds to wait (RFC 9110, section 10.2.3). Today the limiter covers every operation. A 429 of a handler, such as `invitation.daily_limit_reached`, sends no `Retry-After`, so the header is not required. A test enforces it (`RetryAfterDocumentTests`).
- The validators are the one source of a request's limits (the maintainer's decision in audit fix 09). The document writes each rule that it can read: `minLength` and `maxLength`, `format: email`, and `pattern` where ECMAScript reads the regex as .NET does (N11). A length that the API counts without the spaces around the value is a length rule too (`TrimmedMaximumLengthValidator`), so the document holds the limits of a user's names, a suspension's reason and a tenant's name. A rule written as a predicate (`Must`) has no form to read, so the document leaves it out, and so is the time zone's regex. A test lists each rule that the document leaves out. A description names the API's limit, never its number, and says where the API trims a value before it counts its length. A test enforces the lengths, the emails and the patterns, that every `too_long` rule is a length rule, and that no description types the number of a limit (`OpenApiContractTests`).
- Every operation requires the `http` `bearer` scheme of the document. No operation in the document is anonymous. A test enforces it.
- Every property of a response schema is required, unless it may be null. A page's `items`, `page`, `pageSize` and `total` are required. In Problem Details, `code` and `traceId` are required. `errors` and `tenantIds` are absent where they do not apply; the document lets them be null, and the API never sends null. A test enforces it.
- A number in a JSON body is a JSON number. The API reads no JSON number from a string (`JsonNumberHandling.Strict`), and no schema in the document is an integer or a string. A query parameter, such as `page`, is text by nature, and the API reads it as before. A test enforces the document.
- A second shape of a resource carries its audience in the name: platform `GetTenant`, member `GetMyTenant`. The platform reads a tenant in three shapes: `TenantResponse` for a command, `TenantListItemResponse` for an item of its list, and `TenantDetailResponse` for one tenant (step 20k).
- A request or response field that holds permission names is named `permissions`. It is an array of the one schema `Permission`: every name of the permission list (`Permissions` in ControlPlane.Contracts). Today that is `permissions` of `GetMyTenant`, `RoleDetailResponse`, `CreateRoleRequest`, `UpdateRoleRequest` and the details of `role.created`. A test fails for such a field that is not an array of `Permission` (`OpenApiContractTests`). The document lists the platform's permissions too; the API refuses a name outside the tenant pool in a role (400 `role.permission_invalid`).
- The entitlement keys are two enums in the document: `FeatureKey` and `LimitKey`, each in the order of its list (ARCHITECTURE.md, E1, N11i). A key stays a string in every field, as a map's key or a value of `key`, so a client that knows fewer keys still reads an answer. So a client can show every key of the two lists, with its kind, also for a plan that has no value for it.
- A request gives a role by its id, in a field named `roleId`, required (step r4b). A value that is no id, a number or a missing field is a body the endpoint cannot read: 400 `request.invalid`. An id the tenant has not, another tenant's included, answers 404 `role.not_found`.
- A response field that holds a role of the tenant is named `role`, and it is the one schema `RoleResponse`: `{ id, name, builtIn }`. `id` is the role's id, which a request gives back. `name` is the role's stored name (`roles.name`): `owner`, `admin` or `member` for a built-in role, the tenant's own name for a custom role. `builtIn` is true for a built-in role. A built-in role answers `{ "id": "…", "name": "owner", "builtIn": true }`. Six responses hold a role: `MyTenantResponse`, `MyTenantDetailResponse`, `MemberResponse`, `InvitationResponse`, `InvitationPreviewResponse` (null for a finished invitation whose custom role was deleted) and `UserMembershipResponse`. The details of four audit operations hold a role in a schema of Audit's own, `AuditRoleResponse`, `{ id, name, builtIn }` with an `id` that may be null (K3; the details of `member.role_changed` hold two: `oldRole` and `newRole`). A test fails for a response field named `role`, or of either type, that does not refer to its schema (`OpenApiContractTests`).
- The role endpoints answer a role in a second shape, `RoleDetailResponse`: what `RoleResponse` holds, and `permissions`.
- Every list uses one contract: `page`, `pageSize`, `sort`, `q`, and allowed filters. The answer is `{ items, page, pageSize, total }`. A test enforces it (`ListContractTests`).
- `page` starts at `PageRequest.FirstPage`. `pageSize` is `PageRequest.MinPageSize` to `PageRequest.MaxPageSize`, and `PageRequest.DefaultPageSize` when left out. The document states the limits of `page`, `pageSize`, `limit` and `q` from the constants that the API checks (N11).
- `sort` is one field from the list's allowed fields. A leading `-` sorts it descending: `sort=-name`. Left out or empty, the list's default applies, ascending. We allow one field, not a comma list. Every sort ends with the id as the last key, so two items with the same value never change places between two pages. A field that an item can leave empty (`email`, `lastName`) puts those items last in both directions. Source: JSON:API 1.1, "Sorting".
- `q` is a case-insensitive "contains" match on the list's search fields. `%`, `_` and `\` in it match themselves. It is trimmed. An empty `q` is no filter. It is at most `ListRequest.SearchMaxLength` characters.
- A filter takes one value: the value of the same field in the response. An empty enum, id or email filter value is no filter, as an empty `sort` or `q` is; an empty boolean filter is refused (below). A filter is an enum, an id (a uuid) named after the field it compares with: `roleId` compares with `role.id` (step r4b), a boolean named after the boolean field of the response it compares with: `isSystemAdmin` (step r12), or an email address named after the field it compares with: `email` of `ListUsers` (step r13). An email filter is plain equality on the address in its one form (ARCHITECTURE.md, section 6, "Rules without an id"), never a search: `q` searches. Its query's validator checks it, so an address that is not one answers 400 `request.validation_failed` with `email_invalid`, and the document gives the parameter `format: email`. A test names each email filter, so no list takes a text filter by accident (`ListContractTests`). A value that is no id, or neither `true` nor `false`, is a value the endpoint cannot read: 400 `request.invalid`. An empty boolean filter is such a value too, because Minimal API reads no empty text as a boolean; a client leaves the filter out instead.
- An unknown sort field answers 400 `paging.sort_invalid`, an unknown filter value 400 `paging.filter_invalid`, and a `q` over `ListRequest.SearchMaxLength` characters 400 `paging.q_invalid`. They join the `paging.*` codes.
- `sort` and each filter but an id, a boolean or an email address are enums in the OpenAPI document; an email filter is a string with `format: email`. A filter refers to the schema of the response enum it takes. `SharedKernel` reads and checks `page`, `pageSize`, `sort` and `q` in one place (`ListRequest`, `ListSort`, `ListFilter`). Minimal API binds an enum by its C# name and ignores the JSON name the document shows, so the sort and filter parameters bind any text and `ListRequest` checks it. A test sends each value the document lists (`ListParameterBindingTests`).
- The audit logs are the exception: a cursor, and no total. `ListAuditEntries` and `ListPlatformAuditEntries` take `cursor` (opaque, optional) and `limit` (the limits and the default of `pageSize`, in `CursorRequest`), and nothing else, apart from `tenantId` of `ListPlatformAuditEntries`: the platform's entries about that tenant. A cursor holds a place in the whole log, so a next page sends the same filter. The order is newest first, by `occurred_at`, then `id`, both descending; the cursor holds the last item's pair. The answer is `{ items, nextCursor }`, and `nextCursor` is null on the last page. A cursor that does not decode, or was changed, answers 400 `paging.cursor_invalid`; a limit out of range, 400 `paging.limit_invalid`. A test allows the cursor contract for these two operations only (`ListContractTests`).
- An audit log's order has a B-tree index: `(tenant_id, occurred_at, id)` on `audit.entries`, `(occurred_at, id)` on `audit.platform_entries`, and `(target_kind, target_id, occurred_at, id)` on `audit.platform_entries` for its tenant filter.
- Every field that is searched or sorted has an index. A searched field has a trigram GIN index (PostgreSQL `pg_trgm`), because a B-tree index cannot serve a "contains" match. A sorted field has a B-tree index. Source: PostgreSQL documentation, "pg_trgm", "Index Support".

- The member search starts from the active tenant's memberships, which row level security keeps to the tenant, and joins each member's user. It never starts from the users table, which is not under row level security (R6).

### K6. Concurrency

- Every handler that changes data, a saga step included, first locks the root row of each aggregate it changes (`SELECT … FOR UPDATE`); a transaction changes more than one aggregate only as ARCHITECTURE.md, M2, allows. Updating a tenant locks that tenant's row; updating an invoice locks that invoice's row, never the tenant's.
- In ControlPlane, memberships and invitations belong to the tenant aggregate, and "at least one Owner" is the tenant's rule. So a change to them locks the tenant row.
- A rule that only keeps a value unique uses a database constraint (a unique index), not a lock.
- Locks are taken in one order: the aggregate root first. A lock lives only inside one transaction, never across two HTTP requests.
- Sources: Kleppmann, *Designing Data-Intensive Applications*, chapter 7, "Write Skew and Phantoms". Fowler, *Patterns of Enterprise Application Architecture*, "Coarse-Grained Lock". Evans, *Domain-Driven Design*, chapter 6, "Aggregates". Vernon, "Effective Aggregate Design". PostgreSQL documentation, "Explicit Locking".

### K8. Language and time zone

### K9. The platform's Owner invitation

- A tenant has no Owner only when its first Owner never accepted (K1). The platform then invites an Owner: `InviteOwner`, `POST /v1/platform/tenants/{tenantId}/invitations`.
- At most one platform Owner invitation is pending at a time; the one `CreateTenant` sends counts. A new one replaces the pending one, also for another email: the old one becomes `Cancelled`, and its link answers 404 `invitation.not_found`, as a revoked one (K2). Accepting cancels nothing.
- `InviteOwner` locks the tenant row and counts the Owners under the lock (K6). A tenant that is not active answers 409 `tenant.not_active`; one with an Owner 409 `tenant.has_owner`. An acceptance locks the same row first, so it runs before, and the invitation is refused, or after, and finds its invitation cancelled: never two pending, never a cancelled link that joins.
- The rule is the tenant's (`Tenant.Invite`, M1).
- Each record is the platform's action: `tenant.owner_invited`, in both logs, with the tenant as the target (K3).
- The summary of K10 shows the invitation on the platform's screens while the tenant has no Owner.

### K10. The tenant's summary

- The platform's list reads across tenants, where row level security hides the memberships and the invitations (R1, R5). So each tenant has a summary in a row of its own, in `tenant_summaries`: how many members and Owners it has, and its latest Owner invitation (R12; the maintainer's decision in step 20k).
- One place writes it: `ITenantRepository.SaveAsync`, from the tenant's own rows, after it saves the transaction's changes. Every command that changes a membership or an invitation saves through it under the tenant's lock (K6): `CreateTenant`, `AcceptInvitation`, `InviteMember`, `RevokeInvitation`, `ChangeMemberRole`, `RemoveMember`, `RemoveUserMembershipCommand`, `CloseTenant` and `InviteOwner`. `RecordSignUpCommand` saves through it too, although the summary does not show what it changes. A transaction that saves such a change without it does not commit (ARCHITECTURE.md, R12). A test compares the summary with the rows after the commands of the platform and the tenant web, the race tests included (`TenantSummaries`); `RecordSignUpCommand` has no such test.
- The Owner invitation's email is personal data. The row keeps it only while the tenant has no Owner, and clears it when an Owner joins. The state `expired` comes from the expiry at the moment of a read, never from a stored value.
- A membership keeps when its user joined (`joined_at`). `GetTenant` lists the Owners by it, then by the user id. The summary names no Owner (the maintainer's decision in step r2a).

### K11. The user's membership count

- The platform's user list shows how many tenants each user is in. It reads across tenants, where row level security hides the memberships (R1, R5), and a tenant's transaction cannot declare the user too (R4). So the user row keeps the count: `membershipCount` (ARCHITECTURE.md, R13).
- It changes by one, in the command's own transaction, under the tenant's lock (K6): `AcceptInvitation` adds one, `RemoveMember` and `RemoveUserMembershipCommand` take one away. The database adds the change to the stored value, so two tenants' commands for one user never lose one. A test compares the count with the rows after each of them.
- `AcceptInvitation` locks a known user's row for an update, not a share lock, so two acceptances of one user in two tenants run one after the other.
- A deleted user has no membership, so their count is 0.

### K12. The invitation preview

- `GetInvitationPreview` lets the accept screen name the tenant, the inviter and the role, and say when the link is expired, used or cancelled, before the person accepts.
- It is a POST with the code in the body: the code is the invitation's secret, and a URL ends up in access logs, the browser's history and `Referer` headers (RFC 9110, section 17.9).
- It finds the invitation as `AcceptInvitation` does: the tenant of the code is declared, then the invitation is found by the hash of the secret (T2).
- An unknown code answers 404 with the body `AcceptInvitation` gives, so a code cannot be probed. A caller without the invited address answers 403 `invitation.email_mismatch`, with the body `AcceptInvitation` gives, before the state is read: a forwarded link tells its holder only what the email told them, the tenant's name and the link's lifetime (the maintainer's decision in step 20l). The body holds no address.
- The platform's invitation names the platform (`kind` `platform`), never the system admin.
- It reads only: it changes nothing and writes no audit entry (K3).

### K13. Owner recovery

- The platform makes an existing member of a tenant an Owner: `MakeOwner`, `POST /v1/platform/tenants/{tenantId}/owners`, with the member's user id from the user's detail (`GetUser`). The maintainer's decision M2 in the review of 2026-10-21.
- It works whether or not the tenant has an Owner. The only Owner may have left the company and not answer: the tenant has an Owner on paper, but nobody can manage it. The old Owner stays, and the new Owner can remove them (K1). GitHub and Slack transfer ownership in the same way.
- The platform otherwise adds no member and gives no other role. It acts on the Owner only: the first Owner at creation, an Owner invitation for a tenant without one (K9), and this action.
- Only an active tenant, as for K9. A member who is an Owner already answers 409 `member.already_owner`; a suspended or a deleted user 409.
- The rule is the tenant's (`Tenant.MakeOwner`, `flows/owner-recovery.md`). The escalation rule does not apply: the actor is the platform, not a member.
- Each record is the platform's action (K3). The platform's log keeps `tenant.owner_made`, with the tenant as the target, so the platform's log filtered by the tenant shows it. Its details are `TenantOwnerMadeDetailsResponse`: `{ operation, userId, oldRole }`, with `oldRole` an `AuditRoleResponse`. The tenant's log keeps `member.role_changed`, with the member as the target and `MemberRoleChangedDetailsResponse`, `{ operation, oldRole, newRole }`. The event is `OwnerMadeEvent`, of its own, as `OwnerInvitedEvent` is for K9.
